# XOD data model

XOD starts local-first with SQLite. IDs are UUID strings generated by the backend; timestamps are UTC ISO-8601 strings. A local single-user profile is implicit in Phase 2, so a `users` table is intentionally deferred until authentication is a real requirement.

## Implemented tables

| Table | Responsibility |
| --- | --- |
| `conversations` | A durable discussion container; Phase 1 exposes create, list, and reopen routes. |
| `messages` | Ordered user or XOD messages attached to a conversation; Phase 1 writes a successful pair together. |
| `beliefs` | Current statement, confidence, epistemic state, and active version. |
| `belief_versions` | Immutable historical wording/confidence/status snapshots, with an optional source Tribunal message. |
| `evidence` | Provenance-bearing material that supports or contradicts a belief, including source type, optional URL, retrieval time, reliability, and relevance. |
| `predictions` | Predeclared measurable expectations with success criteria, an optional resolution date, an explicit outcome, and a confidence snapshot for new records. |
| `belief_falsification_conditions` | Observable conditions under which a belief should be significantly revised or abandoned. |
| `objections` | Structured objections associated with a belief or analysis. |
| `analyses` | A validated Tribunal payload linked one-to-one with its XOD conversation message. |
| `self_critique_evaluations` | A versioned deterministic rubric result for one Tribunal analysis, including its inspectable check outcomes. |
| `specialist_evaluation_measurements` | One upsertable paired baseline/specialist quality, cost, and latency measurement for a fixed evaluation case. |
| `belief_relationships` | Explicit directed links between two distinct beliefs, with a type and optional human note. |
| `failure_reports` | Voluntary, concise records of observed XOD failures, optionally linked to a suite case or Tribunal message ID. |
| `provider_failure_events` | Content-free reliability events for classified provider failures, keyed by unique error ID. |

Experiment execution details, user accounts, and a general analysis-run audit table are deferred because the first useful flows do not need them.

## Invariants

- Confidence is optional but, when present, must be in `[0, 1]`.
- A new belief creates version `1`; changed propositions create a new version rather than mutating history.
- A belief revision creates a new immutable version, even if only confidence or epistemic status changed.
- Evidence direction is `SUPPORTS` or `CONTRADICTS`; a claim is not silently promoted to evidence without source fields.
- Predictions contain a measurable success criterion; they move from `OPEN` to `RESOLVED` once and retain an outcome of `SUPPORTS`, `WEAKENS`, or `INCONCLUSIVE`.
- Resolving a prediction never automatically changes `user_confidence` or `xod_confidence`; calibration policy is an explicitly deferred analytic concern.
- New predictions capture `belief_confidence_at_commit`; earlier predictions remain `NULL` rather than receiving a fabricated historic confidence.
- Falsification conditions are separate durable records, including those captured when a Tribunal proposition becomes a belief.
- A self-critique evaluation is keyed to one Tribunal message and may be recalculated when the rubric changes; it never modifies the original analysis payload.
- `USEFUL` means at least three of four deterministic checks pass. It is not evidence that XOD's reasoning, verdict, or the proposition itself is correct.
- Specialist measurements are user-recorded evaluation data, not model-generated claims. They have one record per fixed seed case so a candidate cannot appear ready through duplicate favorable cases.
- Analytics are derived read models: they preserve no new judgment. Calibration maps `SUPPORTS` to 1 and `WEAKENS` to 0 only as a directional proxy, excludes `INCONCLUSIVE`, and requires five scorable predictions before it becomes available.
- A relationship cannot point from a belief to itself and cannot duplicate the same source, target, and relationship type. Reverse links remain separate intentional records.
- Relationship types are `SUPPORTS`, `CONTRADICTS`, `DEPENDS_ON`, `DERIVED_FROM`, `ALTERNATIVE_TO`, `EVIDENCE_FOR`, `EVIDENCE_AGAINST`, `REQUIRES`, and `UNTESTED_DEPENDENCY`.
- Failure reports store user-entered summaries and optional identifiers, not copied conversation or analysis payloads. They are local SQLite records by default.
- Provider failure events contain only error ID, category, operation, provider/model identifiers, retryability, optional elapsed time, and timestamp. They never store conversation content, prompts, responses, headers, or credentials.
- The database file is created in `data/`, which is ignored by Git.

The executable schema lives in `backend/app/db.py`; it is intentionally small enough to migrate to PostgreSQL later without redesigning the API boundary.
